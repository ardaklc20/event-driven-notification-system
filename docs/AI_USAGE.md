# AI Usage

*Türkçe sürüm aşağıda — [Türkçe](#yapay-zekâ-kullanımı).*

I built this project with AI assistants on purpose: the role is AI-assisted engineering. This file shows how. It covers what the AI produced, how I checked it, and what I rejected or corrected. Every entry is a real event, written down while the work happened.

## 1. Workflow

- **Assistant:** Claude Code (desktop app), model Claude Opus 5.5.
- **Second reviewer:** OpenAI Codex. I give it Claude's decision cards to review and decide on its findings.
- **Method:** a workflow I defined and packaged as a Claude Code skill: the AI turns the brief into testable requirements, lays out each design decision as options with their consequences, and writes code in small, explained pieces; I choose, defend and verify.

| Step | What happens | Output |
|---|---|---|
| 1. Requirements | The AI turns the case PDF into numbered, testable requirements. I review them, ask for re-checks, and approve. | [`REQUIREMENTS.md`](REQUIREMENTS.md) |
| 2. Decisions | For each design question the AI lays out options with consequences (code, testing, failure modes, reversibility). I pick one and write the reason in my own words. | [`DECISIONS.md`](DECISIONS.md) |
| 3. Plan | A second Claude Code skill I wrote, `slice-planner`, which I invoke by hand, turns the requirements and decisions into vertical slices in delivery order: core first, bonus features after. Each slice lists its dependencies and an acceptance check, with the command to run and the expected result. The skill writes only the plan documents; code and Git stay separate steps. I review the plan with OpenAI Codex ([K35](DECISIONS.md)). | [`PLAN.md`](PLAN.md), [`slices/`](slices/) |
| 4. Build | The AI writes code one small piece at a time and explains each piece. Before a slice is committed, I explain why it is built the way it is, and I make every commit myself. Each slice lives on its own branch and is merged through a pull request with a merge commit. | Commits and pull requests |
| 5. Verify | Behaviour is measured with tests and scripts, not by reading code (see section 4). | Test and script output |

## 2. Decisions

The AI proposes; I decide. Every decision, with its reason and its cost, is in [`DECISIONS.md`](DECISIONS.md).

## 5. Rejected or corrected AI output

1. **Design choices disguised as assumptions.** The first requirements list did two things wrong. It stated two design choices as assumptions: per-channel recipient format validation, and filtering dates on `created_at`. It also put design choices into the requirements themselves: status counts for batches, a 409 on cancel, strict priority order, validation at the API, and a "never sent twice" guarantee. I had the AI re-check its assumptions against the case text and moved all of these to the list of open decisions.
2. **Overstated certainty.** The AI labelled "a notification is never sent to the provider twice" as certain. That cannot be guaranteed: if the provider receives a request but the response times out, we cannot know whether it was delivered. I had the AI re-check every claim it had marked as certain, and that check exposed this one. I narrowed the requirement to duplicate requests and concurrent workers and made the delivery guarantee an explicit decision.
3. **A number from the wrong source stated as fact.** The AI wrote that a free webhook.site URL accepts "at most 50 requests". That figure came from the pricing page; the documentation (updated 2026-11-07) says 100. I corrected it and set a rule for the project: when sources conflict, the official documentation wins.
4. **Wrong decision criterion.** For the local container runtime, the AI recommended Colima mainly because it was the option the AI could install by itself, without administrator rights. I rejected that criterion: manual setup steps are mine to do, so options are judged on their merits only. Docker Desktop was chosen ([K0](DECISIONS.md)).
5. **A prediction disproved by measurement.** The AI predicted (labelled "likely") that the Homebrew install of Docker Desktop would not provide the hyphenated `docker-compose` command that the case uses. After installation, `docker-compose version` returned v5.7.0, so the prediction was wrong. No extra package was needed.
6. **Decisions recorded without an owner.** The AI wrote the decision log as impersonal fields ("Decision / Why"), which hid who made each choice and on what grounds. I required every entry to state in the first person what I chose and my own reason for it, and had the log rewritten that way before the first pull request was merged.
7. **An unfair comparison and an unproven capacity claim.** In the queue decision card (K2), Claude warned that River's job state and my notification state could drift apart, but it left out that River can complete a job in the same transaction as my own updates (`JobCompleteTx`). The same card said PostgreSQL "easily" carries 300 messages per second. I gave the card to OpenAI Codex for review. Its findings: the River comparison was unfair, and 3 × 100 = 300 is only the ceiling for sends to the provider, which proves neither the request rate during a campaign nor PostgreSQL's capacity. I had `JobCompleteTx` checked in River's documentation, kept the PostgreSQL table as the queue, recorded River fairly as a close second, and replaced the capacity claim with measurements ([K2](DECISIONS.md)). My later review rounds produced two more fixes: the entry's first wording, "two workers never take the same row", contradicted taking a row back after its lease expires (found by Codex), so I changed it to one valid lease at a time; and K1's comparison mentioned `LISTEN/NOTIFY`, which no decision used (found by Claude), so I removed it, since the first version polls.
8. **A guarantee borrowed from the provider.** In the delivery guarantee card (K3), Claude's main argument and its suggested debrief answer said that the provider would deduplicate retries by an `Idempotency-Key` header; the card mentioned only as a side risk that webhook.site documents no such deduplication. The card also missed a second duplicate window: the worker receives `202` and crashes before writing the result to PostgreSQL. I had OpenAI Codex review the card, and it raised both points. I had webhook.site's documentation checked, kept at-least-once delivery, and rewrote the decision to say plainly when a duplicate is possible; one of the three R11 tests now demonstrates where the guarantee ends ([K3](DECISIONS.md)). In a second review round, Codex showed that the entry's "only in two cases" was too narrow, because a `500` or `504` does not prove the provider did nothing, so I turned the two cases into examples.
9. **Reserved slots that could burst.** In the rate limiter card (K5), Claude proposed that each worker reserve the next free 10 ms slot ahead of time and sleep until it. I had OpenAI Codex review the card. It showed that workers waking up late would then send back-to-back, and that permits spaced 10 ms apart do not by themselves prove the real HTTP sends are spaced the same way. I changed the design so a permit is granted only when its time has come, and I measure R8 on the actual send start times ([K5](DECISIONS.md)). In a later review round, Claude found that the entry left open the order of taking the permit and claiming the notification, which could make a claimed but unsent notification impossible to cancel. I took the problem to Codex and chose its proposal: take both in one transaction.
10. **A quota treated like a temporary limit.** In the retry card (K7), Claude retried every `429` the same way. The card itself noted that webhook.site's quota `429` is permanent, yet still let each notification spend all five attempts on it, and it marked a notification `failed` after the last attempt without saying that this does not prove it was never delivered. I had OpenAI Codex review the card, and it raised both points. I had webhook.site's documentation checked: the response gives no way to tell its `429` cases apart, so I made a provider profile decide; with the free webhook.site profile, a `429` stops automatic retries at once ([K7](DECISIONS.md)). I also set the two reviewers against each other: Codex's first list of retried codes left out `408` and `500`, Claude objected, I took the objection back to Codex, and after it agreed I added both codes.
11. **A requirement that went beyond the case.** Claude wrote R5 as "cancel a notification that has not been sent yet; a cancelled notification is never sent". The case only says "cancel pending notifications", and "never sent" cannot hold with retries, because an earlier attempt may already have reached the provider. I had OpenAI Codex check the requirement against the case text; it found the gap, and I changed R5 to say that a pending notification can be cancelled and that a successful cancel stops any new send attempt ([REQUIREMENTS](REQUIREMENTS.md)).
12. **Requirements that still promised more than the case.** After the fixes in items 1 and 2, two requirements Claude wrote still went beyond the case. R9 said that higher-priority notifications are processed before lower-priority ones, while the case only asks for priority queue support with three levels; the ordering rule is a design choice. R11 said that duplicate requests or concurrent workers never cause a duplicate send, which K3 itself contradicts for unclear provider outcomes. I reviewed both against the case PDF with OpenAI Codex and rewrote them: R9 names the three levels and leaves the order to K8, and R11 names the two behaviours I prove (a repeated request with the same key creates nothing new, and a notification has one valid lease at a time) and points to K3 for where a duplicate is still possible ([REQUIREMENTS](REQUIREMENTS.md)).
13. **A priority guarantee stated too broadly.** In the priority card (K8), Claude did not say which order strict priority guarantees, and it said that `low` waits only when `high` and `normal` together arrive faster than 100 per second. I reviewed the card with OpenAI Codex and researched both points: strict priority fixes the order in which workers take work, not the order in which parallel calls reach the provider, and `low` can starve whenever higher-priority work fills the channel's actual capacity, which can be lower than 100 per second. I kept strict priority and recorded both limits in the decision ([K8](DECISIONS.md)).
14. **An attempt that a crash could erase.** In the status and cancellation card (K9), Claude increased the attempt counter only when a temporary failure was written. I reviewed the card with OpenAI Codex and traced the crash case: a worker dying after its POST would leave that attempt uncounted, and recovering the lease of a fifth attempt could start a sixth POST. I moved the counter into the claim's transaction and made the cancel tests check the general rule that no new POST goes out after a successful cancel ([K9](DECISIONS.md)).
15. **A repeated request answered differently from the first.** In the idempotency card (K10), Claude answered a repeated request with the notification's current state and did not say how a concurrent repeat reads the first request's result. I reviewed the card with OpenAI Codex and researched PostgreSQL's Read Committed rules and the IETF `Idempotency-Key` draft. A repeat now returns the first create response while `GET` shows the current state, and when `ON CONFLICT DO NOTHING RETURNING` comes back empty, a separate `SELECT` reads the stored result ([K10](DECISIONS.md)).
16. **Application limits presented as carrier guarantees.** In the validation card (K11), Claude presented the 160-character SMS limit as one SMS segment and the 1,000-character push limit as fitting the 4 KB payload that APNs and FCM allow. I reviewed the card with OpenAI Codex and researched the SMS encodings and the APNs and FCM limits: 160 code points fill a single segment only when every character is in the GSM-7 set, and JSON escaping can take 1,000 code points past 4 KB. I kept the numbers as documented application limits rather than carrier guarantees, and set the idempotency hash to be computed after the `priority` default is applied ([K11](DECISIONS.md)).
17. **A body size estimate that did not hold.** In the batch card (K12), Claude derived the request body limit from the content limits and arrived at about 41 MB. I reviewed the card with OpenAI Codex and researched JSON escaping: in escaped JSON one emoji can take 12 bytes, so the estimate was wrong. I replaced it with two separate published limits, 1,000 items and a 16 MiB body, and accepted that some large batches get `413` below 1,000 items ([K12](DECISIONS.md)).
18. **A pagination guarantee stated too broadly.** In the listing card (K13), Claude claimed that cursor pagination never repeats or skips a notification. I reviewed the card with OpenAI Codex and researched how PostgreSQL's Read Committed level gives each statement its own snapshot: every page sees the data of its own moment, so a notification whose status changes between pages can enter or leave a filtered result. I narrowed the guarantee to what the cursor does prevent, pages shifted by new notifications, and recorded the rest as a limit ([K13](DECISIONS.md)).
19. **A measurement credited to the wrong point, and a missing integration check.** In the provider card (K14), Claude presented the mock's arrival counter as the proof of R8, drove failure scenarios through a random failure rate in the mock, and planned no check against webhook.site itself, the provider the case names. I reviewed the card with OpenAI Codex and researched the K5 measurement plan and Go's `httptest`: the mock measures when requests arrive, while K5 measures when the worker starts each send. I now report the two separately with retries counted, build the failure scenarios as deterministic tests, and send a synthetic notification through the worker to my own webhook.site URL, with the result in the README ([K14](DECISIONS.md)).
20. **A migration failure described too optimistically.** In the migration card (K18), Claude set goose up with its package-level settings (`SetBaseFS`, `SetDialect`) and said that a failed migration would not leave the schema half-done. I reviewed the card with OpenAI Codex and researched goose's documentation: its Provider API keeps no global state, so the application and the tests can run the same files independently, and because each migration runs in its own transaction, only the failing file is rolled back while the earlier ones stay applied. I switched to the Provider API and recorded the real failure behaviour, with a test that a broken migration keeps the API and the worker from starting ([K18](DECISIONS.md)).
21. **A request body echoed back in errors.** In the OpenAPI card (K19), Claude left open whether Huma could return the stored first response that K10 requires, and it did not notice that Huma v2.41.0 copies a malformed JSON body into its error details. I reviewed the card with OpenAI Codex and researched Huma's documentation and its v2.41.0 source: a `Body []byte` output is written without being serialized again, so the K10 design holds, and the error path does include the raw body. Our error responses now remove that value, and the operations that return raw bytes declare their response schema explicitly ([K19](DECISIONS.md)).
22. **Waiting work labelled by one of its causes.** In the metrics card (K20), Claude counted the notifications waiting for a later time as `waiting_for_retry`, added a `provider_latency_ms` column the first version did not need, and did not say how the values in one response stay consistent with each other. I reviewed the card with OpenAI Codex and researched PostgreSQL's isolation levels and the scheduled notifications bonus: a scheduled notification waits the same way as a retry, and under Read Committed each statement sees its own snapshot. Waiting work is now `deferred`, the provider call duration goes to the logs, and the endpoint reads every value in one `REPEATABLE READ READ ONLY` transaction ([K20](DECISIONS.md)).
23. **A send that a crash could leave unlogged.** In the logging card (K21), Claude logged each provider attempt as a single line. I reviewed the card with OpenAI Codex and traced the K3 crash case: a worker that crashes after its POST may never write that line, so no record would show that the send started, and the R8 measurement would miss it. I split each attempt into a start line and a result line. I also researched the `log/slog` documentation and source: the built-in JSON handler ignores the context it is given, so the ID would appear only through the extra handler the card proposed; the first version passes a logger made with `With` instead ([K21](DECISIONS.md)).
24. **A single command that could report a cached result.** In the test database card (K22), Claude proposed `go test ./...` as the single command. I reviewed the card with OpenAI Codex and researched `go test`'s caching rules: in package list mode it caches successful results and checks only files and environment variables, so a run could print `(cached)` without touching the database. The README command is now `go test -count=1 ./...`. I also removed the template database the card set up from the start; I add it only if measurement shows that applying the migrations to every test database is slow ([K22](DECISIONS.md)).
25. **A call direction that read as an import.** In the project layout card (K23), Claude drew the dependencies as `httpapi → service → postgres`, while the same card defined interfaces where they are used; read as an import, the arrow contradicts that. I reviewed the card with OpenAI Codex and the Go module layout guide: `service` defines the interface and does not import `postgres`, and the entry points in `cmd/` connect the two. The decision now lists the actual imports, with a `go list` check that keeps `postgres` out of `service` and `worker` ([K23](DECISIONS.md)).
26. **A delivery promise stronger than the mechanism.** In the real-time events card (K24), Claude wrote that a connected client would miss no status events, compared events by `updated_at`, and left open the order of subscribing and reading the current state. I reviewed the card with OpenAI Codex and researched PostgreSQL's `LISTEN` and `NOTIFY` documentation: notifications are not replayed for a session that was not listening, and `now()` timestamps are not guaranteed to grow per row, because a transaction can start early and wait for a row lock. I removed the claim, added a `version` column that grows with every status update, and fixed the order: subscribe and buffer, read the snapshot, then pass only newer events ([K24](DECISIONS.md)).
27. **Control frames and shutdown left implicit.** In the WebSocket card (K25), Claude planned a server-only connection that was never read, and it did not say that `http.Server.Shutdown` leaves WebSockets open. I reviewed the card with OpenAI Codex and researched the `coder/websocket` and `net/http` documentation and source: control frames are handled only while a connection is being read, and `Shutdown` neither closes nor waits for hijacked connections. Connections are now read with `CloseRead` and closed through `RegisterOnShutdown`, with a separate wait inside the shutdown budget ([K25](DECISIONS.md)).
28. **A validation rule that would have broken idempotent repeats.** In the scheduling card (K26), Claude ran the "time in the past" rule before the idempotency key, so a repeat of an accepted request would have been rejected once its planned time had passed. I reviewed the card with OpenAI Codex and traced the K10 flow; the key is now checked before the time rule. I also weighed two ways of reporting latency, one distribution for every notification or two separate ones, and chose two, because a deliberately planned wait would otherwise enter the p99 of immediate notifications ([K26](DECISIONS.md)).
29. **One trace promised where the design produces linked traces.** In the tracing card (K27), Claude promised a single Jaeger trace from the API through the worker to the provider, while the same card linked the worker's span to the request instead of making it a child. I reviewed the card with OpenAI Codex and researched OpenTelemetry's messaging conventions: a link connects separate traces. The decision now describes linked traces, limits the first version to three spans, runs Jaeger as an optional Compose profile, and adds a test that notifications still reach `sent` while Jaeger is down ([K27](DECISIONS.md)).
30. **A requirement left without a decision.** While reviewing the decisions against the requirements, I found that R16, the health check endpoint, had no decision: the only health check in the design was PostgreSQL's in Compose (K6), which is not an API endpoint. The AI then mapped every requirement and deliverable to its decisions and found two more gaps: how the image is built (D3) and how configuration is read. Each now has its own decision ([K30](DECISIONS.md), [K31](DECISIONS.md), [K32](DECISIONS.md)).
31. **A mandatory setting that could be empty.** In the configuration card (K32), Claude relied on the library's `required` option for mandatory settings. I reviewed the card with OpenAI Codex and read the `caarlos0/env` v11.4.2 source: `required` only checks that a variable exists, so `DATABASE_URL=""` would pass. Mandatory settings now also use `notEmpty`, and the startup validation also checks the channel limit against R8 and the lease duration against the HTTP timeout and the result-writing budget ([K32](DECISIONS.md)).
32. **A breaker scoped narrower than the failure it guards against.** In the failure handling card (K34), Claude scoped the circuit breaker per channel, although all three channels send to one provider URL. It had no single probe after the cooldown, so every worker could resume at once, and a late success from a call started before the outage would have reset its failure count. The card also put the outage window at 30 seconds, which is only the ceiling of K7's four backoff waits, and included a manual retry endpoint that could resend a notification the provider had already received. I reviewed the card with OpenAI Codex and researched the circuit breaker pattern, whose guidance is one breaker per independent provider and a limited number of trial requests in the half-open state. The breaker is now one per provider, with one probe across all workers and results checked against the breaker's generation, and the manual retry endpoint is out of scope ([K34](DECISIONS.md)).
33. **A draft entry that could lose an accepted notification.** When Claude wrote up the circuit breaker decision (K34), it let any `429` with `Retry-After` open the breaker for every channel, although K7 had left the reach of the provider's quota open and RFC 6585 does not define how a server counts requests. It did not tie the probe slot to the claim and K5's permit, so a worker could take the slot and then find nothing to send. It also worded the generation check so that it covered every result, so a `202` from a call that started before the breaker opened could have been discarded and the notification sent again. I reviewed the entry with OpenAI Codex and researched RFC 6585 and PostgreSQL's locking documentation. A `429` now delays only its own notification unless the provider profile states a shared quota, the probe slot is taken in the claim's transaction and stays free if no notification or permit comes out, and the generation check applies only to the breaker's state ([K34](DECISIONS.md)).
34. **Plan corrections recorded but not applied.** When Claude wrote the delivery plan with my `slice-planner` skill, it kept the corrections from my first plan review as "review items" at the end of four slice notes (11, 12, 13 and 15) instead of writing them into the steps, tests and decisions they changed, while `PLAN.md` said no question was open; slice 11's rule table and its last section described the probe differently. I reviewed the plan again with OpenAI Codex and researched the `coder/websocket` documentation, GitHub's documentation on pull request events and `net/http`'s `RegisterOnShutdown`. That round found six more gaps: a probe answered with a `429` kept the circuit breaker's slot until its lease ended; a 1,000-item batch snapshot is larger than the WebSocket client's default read limit of 32,768 bytes; a permit that was not yet due would have made a worker wait as long as for an empty queue; GitHub tests a pull request's merge commit, not the head commit the release check clones; slice 3's stack check counted arrivals in a shared Compose project; and a template name could carry a NUL character. While checking these, Claude also found that two stack checks set values (`BREAKER_COOLDOWN`, `MOCK_DELAY`) that Compose would not pass to their containers. I had every item written into its slice's steps, tests and acceptance checks, updated K29 and K34, and removed the separate lists ([PLAN](PLAN.md)).

## 5. Reddedilen ya da düzeltilen yapay zekâ çıktıları

1. **Varsayım gibi sunulan tasarım kararları.** İlk gereksinim listesinde iki hata vardı. İki tasarım tercihi varsayım gibi yazılmıştı: alıcı formatının kanala göre doğrulanması ve tarih filtresinin `created_at` üzerinde çalışması. Ayrıca gereksinimlerin içine tasarım tercihleri yerleştirilmişti: batch için durum sayıları, iptalde 409, katı öncelik sırası, doğrulamanın API'de yapılması ve "asla iki kez gönderilmez" garantisi. Yapay zekâya varsayımlarını case metnine karşı yeniden kontrol ettirdim ve bunların hepsini açık kararlar listesine taşıdım.
2. **Abartılmış kesinlik.** Yapay zekâ "bir bildirim provider'a asla iki kez gönderilmez" ifadesini kesin olarak etiketlemişti. Bu garanti edilemez: provider isteği alır ama yanıt zaman aşımına uğrarsa, mesajın gidip gitmediğini bilemeyiz. Yapay zekâya kesin diye işaretlediği her iddiayı yeniden kontrol ettirdim; bu kontrol bu hatayı ortaya çıkardı. Gereksinimi tekrar eden istekler ve aynı anda çalışan worker'larla sınırladım ve teslim garantisini ayrı bir karar haline getirdim.
3. **Yanlış kaynaktan gelen sayının kesin bilgi gibi yazılması.** Yapay zekâ ücretsiz webhook.site URL'sinin "en fazla 50 istek" aldığını yazdı. Bu sayı fiyat sayfasından geliyordu; doküman (2026-11-07'de güncellenmiş) 100 diyor. Düzelttim ve proje için bir kural koydum: kaynaklar çeliştiğinde resmi doküman esas alınır.
4. **Yanlış karar ölçütü.** Yerel konteyner çalıştırıcısı için yapay zekâ, Colima'yı esas olarak yönetici yetkisi gerektirmeden kendisinin kurabildiği seçenek olduğu için önerdi. Bu ölçütü reddettim: elle yapılacak kurulum adımları bana ait, seçenekler yalnızca kendi değerine göre tartılır. Docker Desktop seçildi ([K0](DECISIONS.md)).
5. **Ölçümle çürüyen bir tahmin.** Yapay zekâ, Docker Desktop'ın Homebrew kurulumunun case'te kullanılan tireli `docker-compose` komutunu getirmeyeceğini tahmin etti ("muhtemel" etiketiyle). Kurulumdan sonra `docker-compose version` v5.7.0 döndü; tahmin yanlıştı ve ek paket gerekmedi.
6. **Sahibi belli olmayan karar kayıtları.** Yapay zekâ karar kaydını kişisiz alanlar halinde yazdı ("Decision / Why"); bu, her seçimi kimin hangi gerekçeyle yaptığını gizliyordu. Her kaydın birinci tekil şahısla, neyi seçtiğimi ve kendi gerekçemi söylemesini şart koştum ve kaydı ilk PR birleşmeden önce bu şekilde yeniden yazdırdım.
7. **Haksız bir karşılaştırma ve kanıtsız bir kapasite iddiası.** Kuyruk kararı kartında (K2) Claude, River'ın iş durumu ile benim bildirim durumumun birbirinden ayrışabileceği uyarısını yaptı; ama River'ın bir işi benim güncellemelerimle aynı transaction'da tamamlayabildiğini (`JobCompleteTx`) atladı. Aynı kart PostgreSQL'in saniyede 300 mesajı "rahat taşıdığını" söyledi. Kartı incelemesi için OpenAI Codex'e verdim. Bulguları: River karşılaştırması haksızdı; 3 × 100 = 300 ise yalnızca provider'a gönderimin tavanıdır ve ne kampanya anındaki istek hızını ne de PostgreSQL'in kapasitesini kanıtlar. `JobCompleteTx`'i River dokümanından kontrol ettirdim, PostgreSQL tablosunu kuyruk olarak tuttum, River'ı yakın ikinci olarak adil biçimde kaydettim ve kapasite iddiasının yerine ölçüm koydum ([K2](DECISIONS.md)). Sonraki inceleme turlarımdan iki düzeltme daha çıktı: kaydın ilk ifadesindeki "iki worker asla aynı satırı almaz" cümlesi, lease'i dolan satırın geri alınmasıyla çelişiyordu (Codex buldu), bu yüzden ifadeyi aynı anda tek geçerli lease olarak değiştirdim; K1'deki karşılaştırma hiçbir kararın kullanmadığı `LISTEN/NOTIFY`'dan söz ediyordu (Claude buldu), ilk sürüm polling kullandığı için o notu çıkardım.
8. **Provider'dan ödünç alınmış bir garanti.** Teslim garantisi kartında (K3) Claude'un ana gerekçesi ve önerdiği debrief cevabı, retry'ların provider tarafında bir `Idempotency-Key` header'ıyla tekilleştirileceğini söylüyordu; webhook.site dokümanında böyle bir tekilleştirme olmadığını kart yalnızca yan risk olarak anmıştı. Kart ikinci bir çift gönderim aralığını da atlamıştı: worker `202` alır ve sonucu PostgreSQL'e yazamadan çöker. Kartı OpenAI Codex'e incelettim; iki noktayı da o ortaya koydu. webhook.site dokümanını kontrol ettirdim, at-least-once teslimi korudum ve kararı, çift gönderimin ne zaman mümkün olduğunu açıkça söyleyecek şekilde yeniden yazdım; üç R11 testinden biri artık garantinin bittiği yeri gösteriyor ([K3](DECISIONS.md)). İkinci inceleme turunda Codex, kayıttaki "yalnızca iki durumda" ifadesinin dar kaldığını gösterdi, çünkü `500` ya da `504` yanıtı da provider'ın hiçbir işlem yapmadığını kanıtlamaz; bu yüzden iki durumu örneğe dönüştürdüm.
9. **Patlama yapabilecek önceden ayrılmış slotlar.** Rate limiter kartında (K5) Claude, her worker'ın sıradaki boş 10 ms'lik slotu önceden ayırıp o ana kadar uyumasını önerdi. Kartı OpenAI Codex'e incelettim. Codex, geç uyanan worker'ların bu durumda art arda gönderim yapacağını ve 10 ms arayla verilen izinlerin gerçek HTTP gönderimlerinin de aynı aralıkta olduğunu tek başına kanıtlamadığını gösterdi. Tasarımı değiştirdim: izin yalnızca zamanı geldiğinde veriliyor ve R8'i gerçek gönderim başlangıç zamanları üzerinden ölçüyorum ([K5](DECISIONS.md)). Sonraki bir inceleme turunda Claude, kaydın izin almak ile bildirimi claim etmenin sırasını açık bıraktığını buldu; bu, claim edilmiş ama henüz gönderilmemiş bir bildirimi iptal edilemez bırakabilirdi. Sorunu Codex'e götürdüm ve önerisini seçtim: ikisi aynı transaction'da yapılıyor.
10. **Geçici limit gibi ele alınan bir kota.** Retry kartında (K7) Claude her `429`'u aynı şekilde tekrar denedi. Kart, webhook.site'ın kota `429`'unun kalıcı olduğunu kendisi yazmıştı, ama yine de her bildirimin beş denemesini bunun için harcamasına izin verdi; ayrıca son denemeden sonra bildirimi `failed` olarak işaretlerken bunun bildirimin hiç teslim edilmediğini kanıtlamadığını söylemedi. Kartı OpenAI Codex'e incelettim; iki noktayı da o ortaya koydu. webhook.site dokümanını kontrol ettirdim: cevap iki `429` durumunu ayırt etmenin bir yolunu vermiyor; bu yüzden kararı bir provider profiline bağladım: ücretsiz webhook.site profilinde bir `429` otomatik retry'ı hemen durduruyor ([K7](DECISIONS.md)). İki gözden geçiriciyi birbirine karşı da kullandım: Codex'in tekrar denenecek kodlar için ilk listesi `408` ve `500`'ü dışarıda bırakmıştı; Claude itiraz etti, itirazı Codex'e geri götürdüm ve Codex katılınca iki kodu da ekledim.
11. **Case'in ötesine geçen bir gereksinim.** Claude R5'i "henüz gönderilmemiş bir bildirim iptal edilebilir; iptal edilen bildirim asla gönderilmez" diye yazmıştı. Case yalnızca "bekleyen bildirimleri iptal et" diyor; "asla gönderilmez" ise retry varken tutamaz, çünkü önceki bir deneme provider'a çoktan ulaşmış olabilir. Gereksinimi OpenAI Codex'e case metnine karşı kontrol ettirdim; açığı o buldu ve R5'i, bekleyen bir bildirimin iptal edilebileceğini ve başarılı bir iptalin yeni gönderim denemelerini durdurduğunu söyleyecek şekilde değiştirdim ([REQUIREMENTS](REQUIREMENTS.md)).
12. **Hâlâ case'ten fazlasını vaat eden gereksinimler.** 1. ve 2. maddelerdeki düzeltmelerden sonra Claude'un yazdığı iki gereksinim hâlâ case'in ötesine geçiyordu. R9, yüksek öncelikli bildirimlerin düşük öncelikli olanlardan önce işlendiğini söylüyordu; oysa case yalnızca üç seviyeli öncelik kuyruğu desteği istiyor, seviyeler arasındaki sıra kuralı bir tasarım tercihi. R11, tekrar eden isteklerin ya da aynı anda çalışan worker'ların asla çift gönderime yol açmadığını söylüyordu; K3 ise belirsiz provider sonuçları için bunun tersini kaydediyor. İkisini de OpenAI Codex ile case PDF'ine karşı inceledim ve yeniden yazdım: R9 üç seviyeyi adlandırıyor ve sırayı K8'e bırakıyor; R11 kanıtlayacağım iki davranışı adlandırıyor (aynı anahtarla tekrarlanan istek yeni bir şey yaratmaz ve bir bildirimin aynı anda tek geçerli lease'i olur) ve çift gönderimin hâlâ mümkün olduğu yer için K3'e gönderme yapıyor ([REQUIREMENTS](REQUIREMENTS.md)).
13. **Gereğinden geniş yazılmış bir öncelik garantisi.** Öncelik kartında (K8) Claude, katı önceliğin hangi sırayı garanti ettiğini söylemedi ve `low`'un yalnızca `high` ile `normal` birlikte saniyede 100'den hızlı geldiğinde beklediğini yazdı. Kartı OpenAI Codex ile inceledim ve iki noktayı da araştırdım: katı öncelik, worker'ların işi alma sırasını belirler, paralel çağrıların provider'a varış sırasını değil; `low` ise yüksek öncelikli işler kanalın fiilî kapasitesini doldurduğunda aç kalabilir ve bu kapasite saniyede 100'ün altında olabilir. Katı önceliği korudum ve iki sınırı da karara yazdım ([K8](DECISIONS.md)).
14. **Bir çökmenin silebileceği bir deneme.** Durum ve iptal kartında (K9) Claude deneme sayacını yalnızca geçici bir hata yazılırken artırıyordu. Kartı OpenAI Codex ile inceledim ve çökme senaryosunu izledim: POST'tan sonra ölen bir worker o denemeyi sayılmamış bırakırdı ve beşinci denemenin lease'inin geri alınması altıncı bir POST başlatabilirdi. Sayacı claim'in transaction'ına taşıdım ve iptal testlerini genel kuralı kontrol edecek şekilde kurdum: başarılı bir iptalden sonra yeni POST çıkmaz ([K9](DECISIONS.md)).
15. **İlkinden farklı cevaplanan tekrar istek.** Idempotency kartında (K10) Claude, tekrarlanan bir isteğe bildirimin güncel durumuyla cevap veriyordu ve eşzamanlı bir tekrarın ilk isteğin sonucunu nasıl okuyacağını söylemiyordu. Kartı OpenAI Codex ile inceledim; PostgreSQL'in Read Committed kurallarını ve IETF `Idempotency-Key` taslağını araştırdım. Tekrar eden istek artık ilk oluşturma cevabını alıyor, güncel durumu `GET` gösteriyor; `ON CONFLICT DO NOTHING RETURNING` boş dönerse ayrı bir `SELECT` kayıtlı sonucu okuyor ([K10](DECISIONS.md)).
16. **Taşıyıcı garantisi gibi sunulan uygulama sınırları.** Doğrulama kartında (K11) Claude, 160 karakterlik SMS sınırını tek bir SMS parçası, 1.000 karakterlik push sınırını da APNs ve FCM'nin izin verdiği 4 KB'lık payload'a sığan bir değer olarak sundu. Kartı OpenAI Codex ile inceledim; SMS kodlamalarını ve APNs ile FCM sınırlarını araştırdım: 160 kod noktası tek bir parçayı ancak bütün karakterler GSM-7 kümesindeyse doldurur, JSON kaçışları da 1.000 kod noktasını 4 KB'ın üstüne taşıyabilir. Sayıları taşıyıcı garantisi olarak değil, belgelenmiş uygulama sınırları olarak tuttum ve idempotency özetinin `priority` varsayılanı uygulandıktan sonra hesaplanmasını sağladım ([K11](DECISIONS.md)).
17. **Tutmayan bir gövde boyutu tahmini.** Batch kartında (K12) Claude, istek gövdesi sınırını içerik sınırlarından türetip yaklaşık 41 MB buldu. Kartı OpenAI Codex ile inceledim ve JSON kaçışlarını araştırdım: kaçışlı JSON'da tek bir emoji 12 byte tutabiliyor, yani tahmin yanlıştı. Yerine iki ayrı, yayımlanan sınır koydum: 1.000 öğe ve 16 MiB gövde. Bazı büyük batch'lerin 1.000 öğenin altında da `413` alacağını kabul ettim ([K12](DECISIONS.md)).
18. **Gereğinden geniş yazılmış bir sayfalama garantisi.** Listeleme kartında (K13) Claude, cursor ile sayfalamanın hiçbir bildirimi tekrarlamadığını ya da atlamadığını iddia etti. Kartı OpenAI Codex ile inceledim ve PostgreSQL'in Read Committed seviyesinin her sorguya kendi anlık görüntüsünü verdiğini araştırdım: her sayfa kendi anındaki veriyi görür, bu yüzden durumu iki sayfa arasında değişen bir bildirim filtrelenmiş sonuca girebilir ya da sonuçtan çıkabilir. Garantiyi, cursor'ın gerçekten önlediği şeye, yani yeni bildirimlerin sayfaları kaydırmasına daralttım ve gerisini sınır olarak yazdım ([K13](DECISIONS.md)).
19. **Yanlış noktaya bağlanan bir ölçüm ve eksik bir entegrasyon kontrolü.** Provider kartında (K14) Claude, mock'un varış sayacını R8'in kanıtı olarak sundu, hata senaryolarını mock'taki rastgele bir hata oranıyla kurdu ve case'in adını verdiği provider olan webhook.site'ın kendisine karşı hiçbir kontrol planlamadı. Kartı OpenAI Codex ile inceledim; K5'teki ölçüm planını ve Go'nun `httptest` paketini araştırdım: mock isteklerin varış anını ölçüyor, K5 ise worker'ın her gönderime başladığı anı. Artık ikisini retry'lar dahil ayrı ayrı raporluyorum, hata senaryolarını deterministik testler olarak kuruyorum ve kendi webhook.site URL'me worker üzerinden sentetik bir bildirim gönderip sonucunu README'ye koyuyorum ([K14](DECISIONS.md)).
20. **Gereğinden iyimser anlatılan bir migration hatası.** Migration kartında (K18) Claude, goose'u paket düzeyindeki global ayarlarıyla (`SetBaseFS`, `SetDialect`) kurdu ve başarısız bir migration'ın şemayı yarım bırakmayacağını söyledi. Kartı OpenAI Codex ile inceledim ve goose'un dokümanını araştırdım: Provider API'si global durum tutmuyor, böylece uygulama ve testler aynı dosyaları birbirinden bağımsız çalıştırabiliyor; her migration kendi transaction'ında çalıştığı için de yalnızca başarısız dosya geri alınıyor, öncekiler uygulanmış kalıyor. Provider API'sine geçtim ve gerçek başarısızlık davranışını, bozuk bir migration'ın API'nin ve worker'ın başlamasını engellediğini gösteren bir testle birlikte kaydettim ([K18](DECISIONS.md)).
21. **Hata cevabında geri dönen istek gövdesi.** OpenAPI kartında (K19) Claude, Huma'nın K10'un istediği kayıtlı ilk cevabı döndürüp döndüremeyeceğini açık bıraktı ve Huma v2.41.0'ın bozuk bir JSON gövdesini hata ayrıntılarına kopyaladığını fark etmedi. Kartı OpenAI Codex ile inceledim; Huma'nın dokümanını ve v2.41.0 kaynak kodunu araştırdım: `Body []byte` çıktısı yeniden serileştirilmeden yazılıyor, yani K10 tasarımı geçerli; hata yolu ise ham gövdeyi gerçekten içeriyor. Hata cevaplarımız artık bu değeri çıkarıyor ve ham bayt dönen işlemler yanıt şemalarını açıkça tanımlıyor ([K19](DECISIONS.md)).
22. **Bekleyen işin, nedenlerinden birinin adıyla etiketlenmesi.** Metrik kartında (K20) Claude, ileri bir zamanı bekleyen bildirimleri `waiting_for_retry` olarak saydı, ilk sürümün ihtiyaç duymadığı bir `provider_latency_ms` kolonu ekledi ve tek bir yanıttaki değerlerin birbiriyle nasıl tutarlı kalacağını söylemedi. Kartı OpenAI Codex ile inceledim; PostgreSQL'in izolasyon seviyelerini ve zamanlanmış bildirim bonusunu araştırdım: zamanlanmış bir bildirim de retry gibi bekler, Read Committed'da ise her ifade kendi anlık görüntüsünü görür. Bekleyen iş artık `deferred`, provider çağrısının süresi loglara gidiyor ve endpoint bütün değerleri tek bir `REPEATABLE READ READ ONLY` transaction'ında okuyor ([K20](DECISIONS.md)).
23. **Bir çökmenin logsuz bırakabileceği bir gönderim.** Loglama kartında (K21) Claude her provider denemesini tek bir log satırı olarak yazdı. Kartı OpenAI Codex ile inceledim ve K3'teki çökme senaryosunu izledim: POST'tan sonra çöken bir worker o satırı hiç yazmayabilir; o zaman gönderimin başladığını gösteren bir kayıt kalmaz ve R8 ölçümü o gönderimi kaçırır. Her denemeyi bir başlangıç ve bir sonuç satırına böldüm. Ayrıca `log/slog` dokümanını ve kaynak kodunu araştırdım: hazır JSON handler kendisine verilen context'i yok sayıyor, yani ID ancak kartın önerdiği ek handler ile eklenirdi; ilk sürümde onun yerine `With` ile oluşturulmuş bir logger aktarılıyor ([K21](DECISIONS.md)).
24. **Önbellekten sonuç bildirebilecek tek komut.** Test veritabanı kartında (K22) Claude tek komut olarak `go test ./...` önerdi. Kartı OpenAI Codex ile inceledim ve `go test`'in önbellek kurallarını araştırdım: paket listesi modunda başarılı sonuçları önbelleğe alıyor ve yalnızca dosyaları ve ortam değişkenlerini kontrol ediyor; yani bir çalıştırma veritabanına hiç dokunmadan `(cached)` yazabilir. README'deki komut artık `go test -count=1 ./...`. Kartın baştan kurduğu şablon veritabanını da çıkardım; her test veritabanına migration uygulamak ölçümde yavaş çıkarsa ekleyeceğim ([K22](DECISIONS.md)).
25. **Import gibi okunan bir çağrı yönü.** Proje yapısı kartında (K23) Claude bağımlılıkları `httpapi → service → postgres` diye çizdi; aynı kart arayüzlerin kullanıldıkları pakette tanımlanacağını da söylüyordu ve ok bir import olarak okunursa bununla çelişiyor. Kartı OpenAI Codex ile ve Go'nun modül yerleşimi rehberiyle inceledim: arayüzü `service` tanımlıyor ve `postgres`'i import etmiyor; ikisini `cmd/` altındaki giriş noktaları birbirine bağlıyor. Karar artık gerçek import'ları listeliyor ve `postgres`'in `service` ile `worker`'a girmediğini bir `go list` kontrolüyle gösteriyor ([K23](DECISIONS.md)).
26. **Mekanizmanın verebileceğinden güçlü bir iletim vaadi.** Gerçek zamanlı olaylar kartında (K24) Claude, bağlı bir istemcinin hiçbir durum olayını kaçırmayacağını yazdı, olayları `updated_at` ile karşılaştırdı ve aboneliğin mi yoksa mevcut durumun okunmasının mı önce geleceğini açık bıraktı. Kartı OpenAI Codex ile inceledim ve PostgreSQL'in `LISTEN` ve `NOTIFY` dokümanını araştırdım: dinlemeyen bir oturuma kaçırdığı bildirimler yeniden gönderilmiyor; `now()` zaman damgalarının da satır başına arttığı garanti değil, çünkü bir transaction erken başlayıp satır kilidini bekleyebilir. İddiayı çıkardım, her durum güncellemesinde artan bir `version` kolonu ekledim ve sırayı sabitledim: önce abone ol ve olayları tamponla, sonra anlık görüntüyü oku, ardından yalnızca daha yeni olayları aktar ([K24](DECISIONS.md)).
27. **Örtük bırakılan kontrol çerçeveleri ve kapanış.** WebSocket kartında (K25) Claude, sunucunun yalnızca yazdığı ve hiç okunmayan bir bağlantı planladı ve `http.Server.Shutdown`'ın WebSocket'leri açık bıraktığını söylemedi. Kartı OpenAI Codex ile inceledim; `coder/websocket` ve `net/http` dokümanını ve kaynak kodunu araştırdım: kontrol çerçeveleri yalnızca bağlantı okunurken işleniyor, `Shutdown` ise hijack edilmiş bağlantıları ne kapatıyor ne de bekliyor. Bağlantılar artık `CloseRead` ile okunuyor ve `RegisterOnShutdown` üzerinden, kapanış bütçesi içinde ayrı bir bekleme süresiyle kapatılıyor ([K25](DECISIONS.md)).
28. **Idempotent tekrarları bozacak bir doğrulama kuralı.** Zamanlama kartında (K26) Claude "geçmiş zaman" kuralını idempotency anahtarından önce çalıştırıyordu; bu yüzden kabul edilmiş bir isteğin tekrarı, planlanan saat geçtikten sonra reddedilirdi. Kartı OpenAI Codex ile inceledim ve K10 akışını izledim; anahtar artık zaman kuralından önce kontrol ediliyor. Gecikmeyi raporlamanın iki yolunu da tarttım, bütün bildirimler için tek dağılım ya da iki ayrı dağılım; ikisini seçtim, çünkü aksi halde bilerek planlanmış bir bekleme anlık bildirimlerin p99'una karışırdı ([K26](DECISIONS.md)).
29. **Tasarımın bağlantılı trace'ler ürettiği yerde tek trace vaadi.** Tracing kartında (K27) Claude, API'den worker üzerinden provider'a uzanan tek bir Jaeger trace'i vaat etti; oysa aynı kart worker span'ini isteğin çocuğu yapmak yerine ona link'le bağlıyordu. Kartı OpenAI Codex ile inceledim ve OpenTelemetry'nin mesajlaşma kurallarını araştırdım: link ayrı trace'leri birbirine bağlar. Karar artık bağlantılı trace'leri anlatıyor, ilk sürümü üç span ile sınırlıyor, Jaeger'ı isteğe bağlı bir Compose profiline alıyor ve Jaeger kapalıyken bildirimlerin yine `sent` durumuna ulaştığını gösteren bir test ekliyor ([K27](DECISIONS.md)).
30. **Kararı olmayan bir gereksinim.** Kararları gereksinimlere karşı incelerken R16'nın, yani health check endpoint'inin, hiçbir karara bağlanmadığını gördüm: tasarımdaki tek sağlık kontrolü Compose'daki PostgreSQL kontrolüydü (K6) ve bu bir API endpoint'i değil. Ardından yapay zekâ her gereksinimi ve teslimi kararlarıyla eşleştirdi ve iki açık daha buldu: imajın nasıl derleneceği (D3) ve config'in nasıl okunacağı. Her biri artık kendi kararına sahip ([K30](DECISIONS.md), [K31](DECISIONS.md), [K32](DECISIONS.md)).
31. **Boş kalabilecek zorunlu bir ayar.** Config kartında (K32) Claude zorunlu ayarlar için kütüphanenin `required` seçeneğine güvendi. Kartı OpenAI Codex ile inceledim ve `caarlos0/env` v11.4.2 kaynak kodunu okudum: `required` yalnızca değişkenin var olup olmadığına bakıyor, yani `DATABASE_URL=""` kontrolden geçerdi. Zorunlu ayarlar artık `notEmpty` de kullanıyor; başlangıç doğrulaması ayrıca kanal limitini R8'e, lease süresini de HTTP timeout'u ve sonuç yazma bütçesine karşı kontrol ediyor ([K32](DECISIONS.md)).
32. **Koruduğu arızadan dar kapsamlı bir circuit breaker.** Failure handling kartında (K34) Claude circuit breaker'ı kanal başına kurdu; oysa üç kanal da aynı provider URL'sine gönderiyor. Bekleme süresinden sonra tek bir deneme çağrısı yoktu, yani bütün worker'lar aynı anda devam edebilirdi; kesintiden önce başlamış bir çağrının geç gelen başarısı da hata sayacını sıfırlardı. Kart ayrıca kesinti penceresini 30 saniye olarak verdi; bu yalnızca K7'deki dört backoff beklemesinin tavanı. Bir de provider'ın zaten almış olabileceği bir bildirimi yeniden gönderebilecek bir elle tekrar endpoint'i içeriyordu. Kartı OpenAI Codex ile inceledim ve circuit breaker desenini araştırdım: kılavuzu bağımsız her provider için bir breaker ve yarı açık durumda sınırlı sayıda deneme isteği öneriyor. Breaker artık provider başına tek; bütün worker'lar arasında tek bir deneme çağrısına izin veriyor, sonuçları breaker'ın nesil numarasına göre kontrol ediyor; elle tekrar endpoint'i ise kapsam dışında ([K34](DECISIONS.md)).
33. **Kabul edilmiş bir bildirimi kaybedebilecek bir kayıt taslağı.** Claude circuit breaker kararını (K34) yazarken `Retry-After` taşıyan her `429`'un breaker'ı bütün kanallar için açmasına izin verdi; oysa K7 provider kotasının kapsamını açık bırakmıştı ve RFC 6585 bir sunucunun istekleri nasıl saydığını tanımlamıyor. Deneme çağrısı hakkını claim'e ve K5 iznine bağlamadı; yani bir worker hakkı alıp sonra gönderecek bir şey bulamayabilirdi. Nesil kontrolünü de her sonucu kapsayacak şekilde yazdı; breaker açılmadan önce başlamış bir çağrıdan gelen `202` atılabilir ve bildirim yeniden gönderilebilirdi. Kaydı OpenAI Codex ile inceledim, RFC 6585'i ve PostgreSQL'in kilit dokümanını araştırdım. Artık bir `429`, provider profili ortak bir kota tanımlamadıkça yalnızca kendi bildirimini bekletiyor; deneme çağrısı hakkı claim'in transaction'ında alınıyor ve bildirim ya da izin çıkmazsa boş kalıyor; nesil kontrolü de yalnızca breaker'ın durumuna uygulanıyor ([K34](DECISIONS.md)).
34. **Kaydedilip uygulanmamış plan düzeltmeleri.** Claude teslim planını benim `slice-planner` skill'imle yazarken ilk plan incelememden çıkan düzeltmeleri, değiştirdikleri adımlara, testlere ve kararlara işlemek yerine dört dilim notunun (11, 12, 13 ve 15) sonunda "review items" olarak bıraktı; `PLAN.md` ise açık soru olmadığını söylüyordu. Dilim 11'in kural tablosu ile son bölümü deneme çağrısını farklı anlatıyordu. Planı OpenAI Codex ile yeniden inceledim; `coder/websocket` dokümanını, GitHub'ın pull request olayları dokümanını ve `net/http`'in `RegisterOnShutdown` açıklamasını araştırdım. Bu tur altı boşluk daha buldu: `429` alan bir deneme çağrısı circuit breaker'ın hakkını lease'i bitene kadar tutuyordu; 1.000 öğelik bir batch snapshot'ı WebSocket istemcisinin 32.768 baytlık varsayılan okuma sınırını aşıyor; henüz zamanı gelmemiş bir izin, worker'ı boş kuyruktaki kadar bekletecekti; GitHub bir pull request'in release kontrolünün klonladığı head commit'ini değil, merge commit'ini test ediyor; dilim 3'ün stack kontrolü varışları paylaşılan bir Compose projesinde sayıyordu; bir template adı da NUL karakteri taşıyabiliyordu. Claude bunları kontrol ederken iki stack kontrolünün, Compose'un container'lara geçirmeyeceği değerler (`BREAKER_COOLDOWN`, `MOCK_DELAY`) verdiğini de buldu. Her maddeyi kendi diliminin adımlarına, testlerine ve kabul kontrollerine işlettim, K29 ile K34'ü güncelledim ve ayrı listeleri kaldırdım ([PLAN](PLAN.md)).
